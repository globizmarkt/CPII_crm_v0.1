## 2. DOCTRINAS TÉCNICAS

**Globales que me afectan:**

| Código | Doctrina | Aplicación directa |
|--------|----------|--------------------|
| R3 | Zero-Hex | Ningún color literal en CSS/JS. Solo `var(--token)` o clase semántica Tailwind. |
| R4 | i18n obligatorio | Todo string de UI en capa de traducción. Prohibido texto hardcodeado. |
| ZT | Zero Trust | El ecosistema Skeleton opera bajo este principio. `pending_users` = zona no confiable por defecto. |
| ZS | Zero-Server | Vanilla JS puro. Sin Node runtime en cliente. Sin frameworks implícitos. |

**Doctrinas emergentes (no codificadas oficialmente, surgidas del trabajo real):**

- **Doctrina de Esclusa:** `pending_users` nunca es fuente de verdad. Es zona de tránsito. El esquema Verdent en `/users/{uid}` es la única fuente de verdad del CRM.
- **Doctrina de Transmutación Atómica:** El ETL Landing→Verdent ocurre en una única operación transaccional. No hay estado intermedio persistido.
- **Doctrina de Origen Marcado:** Todo perfil creado fuera del flujo normal (colisión, direct_signup) lleva flag de origen explícito. El sistema nunca asume un perfil limpio sin verificar `meta.origen`.
- **Doctrina de Referral Diferido:** La validación del `referral_code` no bloquea la creación del perfil. Si es inválido, se persiste como `null` + flag para revisión manual. El flujo no se rompe por un código de embajador incorrecto.

## 4. DECISIONES DESCARTADAS Y POR QUÉ

| Decisión | Motivo del descarte |
|----------|---------------------|
| Rechazar autenticación Firebase si no existe doc en `pending_users` | Firebase Auth no es el punto de control correcto para lógica de negocio. Bloquear el Sign-In desde Auth es frágil y viola separación de responsabilidades. La lógica de "perfil incompleto" vive en Firestore/Functions, no en Auth. |
| Cloud Function de barrido para eliminar huérfanos de `pending_users` | Redundante y costoso. El TTL nativo de Firestore (`expireAt`) cubre el borrado automático sin coste operativo adicional. La Function queda solo para auditoría de compliance, no para borrado. |
| Validación de `referral_code` como gate de creación de perfil | Rompería el flujo de onboarding por un dato que puede ser inválido por error tipográfico. Decisión: validación diferida, perfil siempre se crea, el flag permite revisión manual sin fricción para el usuario. |

## 6. CONOCIMIENTO TÁCTICO DEL PROYECTO

**Lo que no está en ningún documento:**

- **"Lux Lusitana" es el nombre de marca, "CPII" es el nombre de proyecto interno.** No mezclar en comunicaciones hacia usuario final.
- **El ecosistema es CRM + MLS privado.** No es un SaaS genérico. Los usuarios son agentes inmobiliarios o similares con relaciones de referido entre ellos. El `referral_code` no es un cupón de marketing — es un vínculo estructural entre agentes que tiene implicaciones de comisión o jerarquía.
- **Zero Trust no es solo una doctrina técnica aquí — es una postura de negocio.** El cliente/Director tiene alta sensibilidad sobre qué datos cruzan qué fronteras. Cualquier propuesta que mezcle zonas (pública/privada) sin esclusa explícita generará fricción aunque sea técnicamente válida.
- **La Landing está blindada políticamente.** No se toca aunque se detecte deuda técnica en ella. Si algo de la Landing es un problema (ej. no escribe `expireAt`), la solución va en el lado Skeleton, no en la Landing.
- **Gemini como Lead Architect tiene veto bloqueante real.** No es un rol ceremonial. En sesiones anteriores su validación ha sido condición necesaria para avanzar. No saltarse este paso aunque la solución parezca obvia.
- **El entorno Zero-Server es una restricción dura, no una preferencia.** Cualquier solución que requiera runtime de servidor en cliente (Express, Next, etc.) es descartada automáticamente sin debate.
- **Tailwind se usa en modo CDN/utilidades, sin compilador.** Solo clases del core de Tailwind disponibles en runtime. Sin purge, sin JIT, sin plugins que requieran build step.
- **La colección `/users/{uid}` es sagrada.** Nada escribe en ella excepto la Cloud Function de transmutación. Ningún cliente escribe directamente. Las Firestore Security Rules deben reflejar esto.

## 7. INPUT REQUISITO PARA SPRINT 3 (FASE A — El Gate)

Para operar desde el primer mensaje sin fricción, necesito recibir exactamente:

**BLOQUE A — Esquema Verdent completo**
El documento JSON o TypeScript interface que define `/users/{uid}` al completo. Sin él, la Cloud Function de transmutación es código ciego.

**BLOQUE B — Decisión sobre DT-04 (carrera de condición)**
¿Qué comportamiento es correcto si el mismo email dispara el Sign-In dos veces antes de que el primer proceso de transmutación complete y destruya el doc en `pending_users`? Opciones conocidas: (1) idempotencia por UID — la segunda llamada detecta que `/users/{uid}` ya existe y aborta, (2) lock con campo `procesando: true` en `pending_users` durante la transmutación.

**BLOQUE C — Confirmación de TTL en Landing**
¿La Landing ya escribe `expireAt` en cada documento de `pending_users`? Si no, necesito el plazo acordado (ej. 72h) para que la Cloud Function lo gestione como fallback.

**BLOQUE D — Estructura de la colección de agentes**
Al menos los campos necesarios para validar `referral_code` → `uid_agente`. Sin esto, la lógica de referidos de la transmutación queda como stub.

**BLOQUE E — Reglas de Firestore Security Rules base**
Si ya existen reglas en el proyecto Firebase, necesito verlas antes de escribir las nuevas. Escribir encima de reglas existentes sin conocerlas es riesgo de ruptura silenciosa.
