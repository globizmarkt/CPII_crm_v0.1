## 2. DOCTRINAS TÉCNICAS

### R3 - Rastreo, Respeto, Responsabilidad
- Todo código debe ser auditable: comentarios de contexto en funciones críticas
- Respeto al estado actual: no reescribir lo que funciona sin justificación
- Responsabilidad de output: el código debe ejecutar, no "casi funcionar"

### R4 - Reducción, Reutilización, Robustez, Rendimiento
- Reducción: una función, un propósito. Máximo 50 líneas por función si es posible
- Reutilización: abstraer patrones repetidos, pero sin sobre-ingeniería
- Robustez: manejo explícito de errores, validación de inputs
- Rendimiento: lazy loading, memoización cuando corresponda, evitar re-renders innecesarios

### Vanilla Compliance
- Cero dependencias externas salvo: React, react-dom, librerías estándar del lenguaje
- CSS puro o CSS-in-JS inline, nunca frameworks CSS
- Fetch API para HTTP, no axios ni wrappers
- JavaScript estándar ES6+, sin transpiladores adicionales
- HTML semántico, accesibilidad base (ARIA cuando se necesita)

### Doctrinas específicas emergentes (no codificadas oficialmente)
- **Principio de Localidad**: estado cerca de donde se usa, no en contextos globales salvo justificación
- **Claridad sobre Cleverness**: código legible > código compacto
- **Errores Ruidosos**: mejor un error visible que un fallo silencioso
- **Documentación Just-In-Time**: comentar decisiones no obvias en el momento, no después

### Patrones generales a evitar (aprendidos)
- **Contextos React globales para todo** — Se vuelven inmantenibles, dificulta debugging
- **Componentes de más de 200 líneas** — Siempre terminan siendo 3 componentes mal ensamblados
- **Validación solo en frontend** — Backend debe validar siempre, frontend es UX
- **Estados derivados duplicados** — Calcular on-the-fly es más seguro que sincronizar caches
- **Callbacks inline complejos** — Extraer a funciones nombradas mejora legibilidad y testing

### Categorías de deuda común a vigilar
- **Manejo de errores inconsistente**: try-catch en algunos lugares, checks en otros
- **Tipado débil en JavaScript**: propTypes o TypeScript ausentes
- **Testing inexistente**: código sin tests unitarios es deuda crítica
- **Documentación desactualizada**: README que no refleja arquitectura real
- **Configuración hardcoded**: URLs, tokens, flags que debieran ser env vars
- **Logging insuficiente**: dificulta debugging en producción
