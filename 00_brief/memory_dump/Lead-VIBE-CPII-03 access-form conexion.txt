### 2. DOCTRINAS TÉCNICAS
* **Doctrina Verdent (Datos):** Los payloads hacia Firestore deben ser estrictamente planos y tipificados: `{ tipo: string, perfil: object, metadata: object }`. Cero anidaciones arbitrarias (`personal`, `location`).
* **Doctrina i18n (Seguridad):** Prohibido el uso de `innerHTML` para inyectar traducciones. Los nodos de texto combinados con estilos se atomizan (ej. `hero.title.main`, `hero.title.highlight`) y se inyectan vía `textContent`.
* **Doctrina UI/Stack:** Vanilla JS + Tailwind CSS (vía CDN). Fuentes: Playfair Display (Display) + Manrope (Body). Iconos: Material Symbols Outlined (URL completa con `opsz,wght,FILL,GRAD`). Paleta: Dark (`#0a0a0a` / `#161513`) y Gold (`#c5a059` / `#C1A85D`).
* **Doctrina de Intervención:** Protocolo `/cartografia_quirurgica`. Declaración de cabecera, índice maestro [SEC-XX], y bloque de coordenadas exactas (UBICACIÓN, ACCIÓN, CÓDIGO ANTERIOR, CÓDIGO NUEVO).

### 4. DECISIONES DESCARTADAS Y POR QUÉ
* **Descarte:** Uso de `innerHTML` en el motor `i18n.js`.
    * *Motivo:* Fragilidad ante inyecciones, rotura de clases CSS anidadas (Tailwind). Se optó por atomizar etiquetas `<span>` y usar `textContent`.
* **Descarte:** Payload Firestore anidado original (`personal.name`, `location.country`, `genealogy.padrino`).
    * *Motivo:* Incompatibilidad con el esquema futuro `Usuario` de Verdent. Se reestructuró a `perfil.nombre`, `perfil.pais`, `perfil.referidoPor`.
* **Descarte:** Asignar `club_manager` directamente al perfil del Lead.
    * *Motivo:* Un Lead es un estado temporal. Se movió a `metadata.club_manager` para que una Cloud Function lo procese al convertirlo en Usuario certificado.
* **Descarte:** Pipeline CI/CD automático (GitHub Actions) para el primer despliegue en GCP/LEMP.
    * *Motivo:* Sobrecarga innecesaria para un MVP. Se optó por un control manual vía SSH (`git pull`) en el directorio Nginx para aislar problemas de Certbot/SSL.
