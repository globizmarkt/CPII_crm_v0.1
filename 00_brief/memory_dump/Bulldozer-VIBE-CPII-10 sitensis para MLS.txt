## 2. DOCTRINAS TÉCNICAS

### Globales (afectan todo el código)

**Google Ecosystem First:** Toda la infraestructura vive en Firebase/GCP. Sin plataformas externas para el core de datos.

**Free First:** Coste base = $0. Escalado a cero. Sin servidores fijos. Sin licencias por usuario.

**Serverless Puro:** Cloud Functions Gen 2 TypeScript. Sin servidores dedicados. Sin gestión de infraestructura.

**Skeleton es agnóstico:** El chasis no sabe nada de inmobiliaria, finanzas CPII ni lógica vertical. Todo lo vertical se inyecta como plugin via `offeringConfig.vertical`.

**Verdad Doctrinal Skeleton (Jerarquía de autoridad):**
1. `project_manifest.json` — Rey
2. `CIFI_AIP_BUSINESS_BLUEPRINT.md` — Ley
3. Carpetas dogfood y entregables — Operativo
4. `MASTER_FLUJO_ENTRADA.md` v2.4 — Referencia base del flujo de onboarding

### Doctrinas específicas emergidas en trabajo real

**Doctrina de la Triple Escritura Atómica:**
El estado de seguridad se sincroniza simultáneamente en 4 capas:
- Firestore `/users/{uid}` — fuente de verdad definitiva
- Custom Claims Firebase Auth Token — barrera en el Edge (rápida, sin consultar Firestore)
- Zustand Store (cliente) — verdad reactiva para la UI
- localStorage — backup de recuperación silenciosa (Adopción Tardía)

**Regla de Tierra Firme:**
Sin `window.location`. Si una condición no se cumple, la escena no existe en el DOM.
SceneManager inyecta `SCENES.BLOCK` o `SCENES.COMPLIANCE_WAITING`.

**Convivencia Paratáctica (árbol Firestore):**
`/users/{uid}` = Esclusa de Identidad (GDPR, KYC, firma legal). Privacidad absoluta.
`/projects/{projectId}` = Contenedor del WebOS. Todo el negocio cuelga aquí.
No se reemplazan. Responsabilidades estrictamente separadas.

**Doctrina del Trigger Tonto:**
`onAuthCreate` es solo el portero. Solo crea `/users/{uid}` e inyecta Claims bloqueados.
La construcción del WebOS ocurre en `crystallizeProject` (Cloud Function HTTP Callable).
El trigger de Auth nunca toca lógica de negocio.

**Protocolo ARB (Pre-vuelo en Store):**
Ninguna Cloud Function escribe directamente en Firestore sin confirmación explícita del usuario.
Flujo: Cloud Function retorna JSON → Zustand valida → usuario confirma → Triple Escritura Atómica.

**Escritura Pasiva para IA:**
Sin Pub/Sub ni EventArc. Frontend escribe en `analytics`/`activity` (solo escritura).
Cloud Functions de IA se activan via `onDocumentCreated`. Coste fijo = $0.

**Recuperación Silenciosa (Adopción Tardía):**
Si el usuario cierra el navegador entre Login y firma del Check 3, `Gatekeeper.verifyAccess()` detecta proyecto huérfano en localStorage.
El sistema nunca crea un segundo proyecto vacío.
`tenant_id` es la identidad; el proyecto vive en localStorage hasta el Sello de Propiedad.

**Estructura Tricameral del Manifiesto:**
```json
{
  "offering": {},    // Configuración dura — Tiers, APY, validaciones — lo lee el Gatekeeper
  "narrative": {},   // Copy, capítulos, pedagogía — lazy load si >400KB en narrative_chunks/
  "gatekeeper": {}   // Estados de los Checks — legalSigned, complianceStatus
}
```

**AIMON Cerebro Dual:**
- Cerebro Rápido: nodo `glossary`/`pedagogy_cache` en JSON local. Coste $0. Respuestas cacheadas.
- Cerebro Lento: Vertex AI. Solo escala si pregunta está fuera del ADN predictivo (`dirty: true`).
- Cuando escala: `globalBus` emite evento → renderiza `<gd-aimon-typing>` → sin UI Flicker.

**Naming Verdent:**
- Interfaces: PascalCase (`ActivoInmobiliario`, `VentanaInversion`)
- Funciones: camelCase (`calcularComisionesRed`, `liquidarVentana`)
- Constantes: UPPER_SNAKE_CASE (`REV_SHARE_L1`, `FONDO_SOSTENIBILIDAD_PCT`)

**7 Leyes Inmutables (selladas en último sprint):**
1. `crystallizeProject` atómico — valida tenant_id vs Claims antes de escribir
2. globalBus nunca bloquea hilo principal — todo asíncrono reactivo
3. `WorkspaceManager.loadView()` ejecuta `destroy()` obligatorio — mata listeners fantasmas
4. AIMON usa Skeleton Screen `<gd-aimon-typing>` cuando escala a Vertex AI
5. `tenant_id` solo se escribe en `allow create` — prohibida su mutación en `allow update`
6. Revenue Share y liquidaciones usan Sharded Counters + Transactions — sin incrementos simples
7. Binarios viajan directo navegador → Firebase Storage — base de datos solo guarda URL

## 4. DECISIONES DESCARTADAS Y POR QUÉ

- **Colección `pending_users`** — Descartada. El nombre real en producción es `leads`. Usar `pending_users` habría generado deuda de migración innecesaria.

- **`onAuthCreate` como constructor del proyecto** — Descartado. El trigger es el portero, no el constructor. La construcción del WebOS es responsabilidad de `crystallizeProject` (Cloud Function Callable). Mezclar ambas responsabilidades en el trigger habría creado un punto de fallo único y violado la Ley de Idempotencia.

- **Colección separada `/asset_proposals/`** — Descartada. Los activos viven en `/assets/{assetId}` con campo `estado` como máquina de estados pura. Una colección separada habría duplicado lógica y complicado las Security Rules.

- **Extension Firebase Trigger Email para mailer** — Descartado. Se optó por Cloud Function Gen 2 + Cloud Tasks para tener control de segmentación, retry personalizado y válvula de escape a SendGrid en burst mode. La extensión no permite lógica condicional de routing.

- **Arrays de descendencia en documento de usuario** — Descartado. Límite de 1 MiB de Firestore y complejidad de actualización. Se adoptó Flat Aggregation: ancestry array (ascendientes, máximo 10 niveles) + sharded counters + `/referidos` subcollection.

- **Redis para caché** — Prohibido por doctrina. Rompe el escalado a cero y el principio Free First.

- **React/Vue/Angular para frontend** — Prohibido por doctrina. Se usa Vanilla JS + Web Components en Light DOM.

- **Shadow DOM en prototipos Stitch** — Descartado para prototipos. Tailwind CDN no penetra el Shadow DOM, lo que rompe el sistema de temas. Se usa Light DOM en prototipos; el encapsulamiento se implementa en la fase de integración por Gemini.

- **Pub/Sub y EventArc para telemetría de IA** — Descartado. Viola principio Free First. Coste fijo de infraestructura de mensajería. Reemplazado por Escritura Pasiva + `onDocumentCreated`.

- **innerHTML para datos dinámicos** — Prohibido. Vulnerabilidad XSS. Se usa `textContent` o motor `data-i18n` con `data-i18n-html="true"` para contenido enriquecido validado.

- **Herencia del consentimiento RGPD de la Landing al CRM** — Descartado. El Check 3 (Legal) exige firma inmutable nueva en el túnel privado. El consentimiento de la landing no se hereda por diseño.

- **Colores hexadecimales hardcodeados en clases Tailwind** — Prohibido. Viola el principio de agnosticismo temático. Todo via CSS Variables en `:root`.
