### 2. DOCTRINAS TÉCNICAS
**Oficiales codificadas:**
* **R0 (Agnosticismo Radical):** Cero hardcode de cliente/vertical. Todo debe inyectarse vía `offeringConfig` o `data-i18n`.
* **R1-R2 (Vanilla & Light DOM):** Cero frameworks JS (React, Vue prohibidos). Componentes web nativos renderizados en Light DOM para compatibilidad con Tailwind CDN.
* **R3 (Tematización Lux Lusitana):** Variables CSS estrictas (`--theme-bg: #161513`). Cero colores hexadecimales directos en el código.
* **R4-R5 (i18n Global):** Atributos `data-i18n` y `data-i18n-html` para inyección de traducciones (PT/ES/EN/FR).
* **R6 (SceneManager):** Navegación sin recargas, prohibidos los enlaces `<a href=".html">`.
* **R7 (Tierra Firme):** Si un check del Gatekeeper falla (ej. `kyc_status != 'verified'`), la escena no se oculta con CSS, directamente no existe en el DOM.

**Tácitas / Emergentes (Aprendizaje de Sprint):**
* **Lienzo Flotante (Atmósfera):** El Layout Trinity (250px LSB / flex Canvas / 320px RSB) no debe tener bordes duros. El espacio y las sombras (`shadow-lg`) separan las zonas.
* **Sistema de Pestañas Independientes (TDI):** Gestión de memoria mediante estados "Activo" (en el DOM) e "Hibernado" (serializado, coste 0 memoria).
* **Doctrina Free First:** `localStorage` primero como buffer. Firestore solo recibe datos cuando hay que sincronizar (Escritura Pasiva o mutaciones críticas).
* **Triple Escritura Atómica:** Todo cambio crítico afecta simultáneamente a Firestore → Custom Claims → Zustand Store mediante transacciones o batches.

### 4. DECISIONES DESCARTADAS Y POR QUÉ
* [Caché en Redis / Memorystore para Autofinancing] — Descartado porque el stack CPII está cerrado en Firebase/GCP puro. Se usa Firestore con TTL nativo (`expireAt`).
* [500 listeners simultáneos para PrescriptorTree] — Descartado por coste prohibitivo en lecturas de Firestore. Se usa 1 listener en snapshot agregado y lazy loading por nodo.
* [Cloud Function intermediaria para mostrar Whitepaper] — Descartado por latencia (cold starts) y coste de egress. Se usa Storage con `allow read: if true` e inmutabilidad garantizada por hash/firma.
* [Campo "availableToKycLevels" en DealRoom] — Descartado por ser semánticamente débil. Se reemplazó por `gatekeeperChecksRequired: [3, 4]` para forzar la firma de T&C y KYC verificado.
* [Borrar código hardcodeado (CIFI-AIP) de inmediato] — Descartado. El "sustrato pedagógico" es necesario visualmente para los dueños. Se aborda como un "Desanclaje Estructural" posterior.

### 6. CONOCIMIENTO TÁCITO DEL PROYECTO
* **La Trampa del Whitepaper:** No es un folleto de ventas. Es el ADN auditable ("Proof of Work") del modelo de incubadora. El campo `visibility` siempre es "PUBLIC", restringiendo el acceso internamente solo a ciertas secciones, no al documento raíz.
* **Sensibilidad del Inversor (CPII):** El sistema debe transmitir "exclusividad flotante". Un inversor retail (desde 100€) debe sentir que entra a un club privado de ultra-lujo, no a un SaaS contable.
* **Dependencia Positiva (Monetización):** El upgrade de Freemium a Enterprise se logra por "autoconvencimiento", no por paywalls agresivos. El sistema enseña a ganar dinero, y cuando el usuario necesita escalar, paga voluntariamente.
* **El Veto de KAIROS:** KAIROS no es solo un auditor, tiene poder de veto real mediante validación de firmas `ed25519`. Ninguna escritura crítica pasa al sistema si falla la validación criptográfica asíncrona.
